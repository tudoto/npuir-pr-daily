CV Pipeline：目标、核心 Pass 与总体框架

基线：4a26b5f94（整理日期 2026-08-18）。主要源码为 bishengir/lib/Dialect/HIVM/Transforms/CVPipelining.cpp、bishengir/lib/Dialect/HIVM/Transforms/regbase/CVPipelining.cpp 以及 A3/A5 的 HIVMPipelines.cpp。

1. 一句话理解

CV Pipeline 是面向 MixedCV kernel 的 Cube–Vector 软件流水优化。它把同一个循环中交错执行的 Cube（AIC）和 Vector（AIV）工作拆成多个可独立推进的阶段，并使用双缓冲或多缓冲传递阶段间数据。最终目标是让第 i 轮的 Cube 计算与第 i-1 轮的 Vector 计算重叠，减少两类核心互相等待造成的流水空泡。

2. 它是不是一个 Pass？

从 MLIR 注册角度看，核心变换确实是一个函数级 pass：cv-pipelining，对应 CVPipeliningPass，运行对象是 func::FuncOp。但从完整功能角度看，“CV Pipeline”更准确地说是一组 pass 共同实现的跨阶段机制，CVPipelining 只负责其中最核心的循环排布和数据通道重构。内存扩容、地址规划、跨核/核内同步、槽位轮转以及 preload 控制流都需要上下游 pass 配合。

核心 pass 的 TableGen 描述是：Cube and vector core pipelining for multi-buffer'ed mix-cv ops。它运行在 HIVM 的 pre-bufferization 阶段，此时 IR 仍以 tensor SSA 和 scf.for 为主。选择这一阶段是因为拆分循环、追踪 use-def、修改 iter_args 和扩展 tensor，在 bufferization 前更容易保持语义完整。

3. 为什么需要 CV Pipeline？

MixedCV kernel 通常把矩阵计算交给 Cube 核，把激活、归约、格式处理等工作交给 Vector 核。未经流水化时，同一循环迭代往往表现为 Cube(i) → Vector(i) → Cube(i+1) → Vector(i+1)；即使两类核心物理上能够并行，数据依赖和单缓冲也会让它们近似串行。Cube 工作时 Vector 可能空闲，Vector 工作时 Cube 也可能等待中间 buffer 被消费。

CV Pipeline 把“迭代内串行”改造成“跨迭代重叠”。例如使用双缓冲后，Cube 可以把第 i 轮结果写入 slot i % 2，Vector 同时从另一 slot 读取上一轮结果。这样两个核心各自沿独立阶段前进，只在真实生产者—消费者依赖和 buffer 复用边界上同步。

未流水化：
时间 ──────────────────────────────────────────────>
Cube    C0        C1        C2        C3
Vector      V0        V1        V2        V3
        大量阶段等待，同一中间 buffer 不能并行读写

流水化后：
时间 ──────────────────────────────────────────────>
Cube    C0    C1    C2    C3
Vector        V0    V1    V2    V3
              ↑ 从这里开始 Cube(i) 与 Vector(i-1) 重叠

它优化的是执行重叠，而不是减少算法计算量。收益取决于 Cube/Vector 工作是否足够均衡、跨阶段数据是否适合多缓冲，以及新增 buffer 和同步成本是否可接受。流水深度越大不一定越快，因为更深的流水会增加 workspace、L1 或 UB 占用，也会扩大数据 live range。

4. 核心 Pass 的输入与输出

输入特征

  • 运行对象是 func.func 中的 scf.for。
  • 循环内包含能够被识别为 Cube 或 Vector 的操作。
  • InferFuncCoreType、MixedCV load/store 插入和 MarkMultiBuffer 已经提供核类型、通信与多缓冲信息。
  • pipeline depth 不能是 0 或 1；当前实现遇到 AIC BatchMatmul loop 会直接跳过。

输出特征

  • 原循环被按 WorkItem 重新组织；Unroll 模式生成新的流水循环，Skew 模式生成带 preload scope/标记的结构。
  • 跨 WorkItem 的 tensor、workspace 或 loop-carried value 被显式识别并转接。
  • 需要并行在途的数据增加一个多缓冲槽位维度，或使用扩展 workspace。
  • 生成的 IR 为后续 PlanMemory、同步求解和 EnableMultiBuffer 提供结构与标记。

一个简化的中间数据变化如下：

原中间值：        tensor<M×N>
双缓冲后：        tensor<2×M×N>
第 i 轮写入：     slot = i % 2
第 i-1 轮读取：   另一在途 slot

第一维是 pipeline slot 维，不是原始算法维度。当前实现会通过 hivm.cv_pipelined_multi_buffer 等标记把这一契约传给后续 pass，避免后续分解操作误写整个多缓冲区。最终的 memref 地址和槽位选择仍由后续 lowering 完成。

5. CVPipelining 内部总体框架

5.1 候选循环扫描

Pass 收集函数内的 scf.for，采用 post-order，从最内层循环开始尝试。一个内层循环成功流水化后，它的父循环会被标记为不再尝试，以减少重复变换和编译时间。Pass 不是“看到循环就强制改写”，任何合法性或依赖检查失败都应回退为原循环。

5.2 WorkItem 构建

WorklistBuilder 根据核类型、separator、use-def 和内存关系，把循环体划分为一组 WorkItem。每个 WorkItem 可以理解为一段由 Cube 或 Vector 执行的流水阶段，它保存所属操作、输入输出、workspace、依赖关系和后续克隆所需映射。A3 与 A5 使用不同的 WorklistBuilder/实现类，但总体模型一致。

典型 WorkItem 序列可能是：

WorkItem 0：Cube load + matmul
WorkItem 1：Vector activation
WorkItem 2：Cube accumulation
WorkItem 3：Vector store

划分不能只看操作的直接 core type。实现还需要追踪 view/cast/subview、loop iter_arg、destination-style output、workspace alias、标量控制链和 loop-carried dependence。否则把操作克隆到不同循环后，可能留下指向原循环内部值的悬空引用。

5.3 依赖与输出分析

markOutputs 识别一个 WorkItem 产生、另一个 WorkItem 消费的值，并区分普通局部输出、workspace 输出和循环携带输出。这些值不能像同阶段临时值一样直接克隆，必须通过新循环的 iter_args/results、tensor slice 或 workspace slot 显式转接。checkWorkItemDependencies 会在真正修改 IR 前拒绝当前迁移逻辑无法表达的跨阶段依赖。

源码还包含 merger op、counter、atomic effect、scalar extract 等特殊处理。它们解决的是“操作表面上不是 Cube/Vector 核心计算，但实际连接了阶段或影响循环状态”的情况。无法安全归属到单一 WorkItem 时，pass 选择回退，而不是生成可能错误的流水 IR。

5.4 多缓冲扩展

跨阶段数据如果只有一个 buffer，生产者写下一轮时可能覆盖消费者仍在读取的上一轮数据。Pass 因此为需要并行在途的数据增加 slot 维度，或把 workspace 扩展为多个槽位。Unroll 模式的深度来自 setWorkspaceMultibuffer，常见值是 2，但实现并不限定只能双缓冲。

多缓冲主要解决存储冲突，而不是自动解决执行依赖。后续 PlanMemory 必须为这些 buffer 规划合法地址，GSS 或 InjectSync 必须约束生产、消费和槽位复用，EnableMultiBuffer 才会把标记降低为显式轮转。缺少任一环节，都不能认为完整的软件流水已经落地。

5.5 新循环创建与操作迁移

Unroll 路径通过 createNewLoops 构造新的循环和 iter_args，再由 migrateOps 按 WorkItem 克隆原操作。IRMapping 把原 induction variable、iter_arg、跨阶段结果和 workspace 映射到新值。新循环通过验证后才替换原循环；失败时使用 checkpoint/revert 恢复原始结构。

这一步的本质不是简单 loop unroll。它同时重写了不同核心上的阶段顺序、循环状态传递和跨阶段 buffer 访问。实现复杂度主要来自保持所有 use-def、alias、yield 和控制流语义在拆分后仍然成立。

6. 三种模式

模式当前含义适用情况
Off不加入 CVPipelining；driver 还会关闭对应 workspace multibuffer。建立基线、规避不支持结构或调试问题。
Unroll默认模式。按指定深度构造 WorkItem 流水和多缓冲通道。常规 MixedCV 生产路径。
SkewCVPipelining 先建立 WorkItem、preload scope 和属性，后续 CreatePreload 构造 prime/steady/drain。希望不同阶段错峰启动、隐藏更长延迟。
Dynamic枚举和 CLI 已存在，但标记为 developing。当前核心实现只有 Skew 的独立分支，Dynamic 仍落到非 Skew 的重构路径。不应当作完整动态调度能力使用。

Unroll 模式

Unroll 是默认模式，强调固定深度的多轮在途和阶段重排。它会扩展跨阶段输出、创建替代循环并迁移操作，最终让 Cube/Vector 能处理不同逻辑迭代。这里的 “unroll” 不只是复制循环体，还包含跨核 WorkItem 的依赖转接和多缓冲。

Skew / Preload 模式

Skew 模式把不同 WorkItem 按不同提前量错开。CVPipelining 在 pre-bufferization 阶段建立 scope、workspace 和 hivm.preload_* 类属性；post-bufferization 的 CreatePreload 再扩展控制流，形成 prime、steady 和 drain 三段语义。只运行 CVPipelining 而没有后续 CreatePreload，不能视为完整的 preload 流水。

Prime：   C0
         C1  V0
Steady： C2  V1
         C3  V2
Drain：      V3

Lazy Loading

enableLazyLoading 允许某些 load-like 操作被克隆到多个消费 WorkItem，而不是把 load 结果扩成中间多缓冲。它可能减少中间 buffer 和内存压力，但会增加或复制 load，并要求相关地址 counter 在不同 stage 中保持独立和同步。当前实现特别处理了 Skew 模式下共享 counter iter_arg 的私有化。

7. 在完整 Pipeline 中的位置

flowchart LR A[InsertLoadStoreForMixCV
建立显式 C/V 通信] --> B[InferFuncCoreType
标记 AIC/AIV/MIX] B --> C[MarkMultiBuffer #1
标记候选与深度] C --> D[Canonicalize + InlineOTFBroadcast] D --> E[CVPipelining
拆阶段、重排循环、扩展通道] E --> F[MarkMultiBuffer #2
A5 流水后再识别新候选] F --> G[PlanMemory GLOBAL
规划 workspace] G --> H[Cross-Core GSS / InjectBlockSync] H --> I[SplitMixKernel
拆成 AIC/AIV 函数] I --> J[OneShotBufferize] J --> K[PlanMemory LOCAL
规划 UB/L1 地址] K --> L[CreatePreload
仅 Skew/Preload] L --> M[Intra-Core GSS / InjectSync] M --> N[EnableMultiBuffer
显式槽位轮转]

上游依赖

  • InsertLoadStoreForMixCV / InsertCVTightCoupledBuffer：把跨核数据通信显式化。
  • InferFuncCoreType：提供操作和函数的 AIC/AIV/MIX 归属。
  • MarkMultiBuffer：提供候选 buffer、深度和 preload 相关标记。
  • Canonicalize、InlineOTFBroadcast：清理阻碍 WorkItem 分析的结构。

下游消费者

  • PlanMemory(GLOBAL/LOCAL)：为扩展后的 workspace、L1 和 UB buffer 分配地址并检查容量。
  • CrossCoreGSS / DelayedCrossCoreGSS / InjectBlockSync：处理 Cube 与 Vector 之间的同步。
  • SplitMixKernel：把流水化后的 MIX 函数拆成 AIC 与 AIV 函数。
  • CreatePreload：把 Skew 标记展开为 prime/steady/drain 控制流。
  • GraphSyncSolver / InjectSync：处理各核心内部的依赖和 buffer 复用同步。
  • EnableMultiBuffer：把多缓冲属性降低为 %iv % depth 一类槽位选择和显式地址轮转。

8. A3 与 A5 的差异

项目A3 mem-basedA5 RegBase
核心实现Transforms/CVPipelining.cpp，CVPipelineImplTransforms/regbase/CVPipelining.cpp，CVPipelineRegbaseImpl
Worklist通用 WorklistBuilderRegBase 专用 WorklistBuilder
通信准备主要通过 InsertLoadStoreForMixCV非 Triton A5 主要使用 InsertCVTightCoupledBuffer 与标量 load/store
内存规划PlanMemoryPlanMemoryRegBase，额外考虑 VF、TCB 和 RegBase UB/L1 约束
Skew 前置通用 workspace/preload 标记在 Skew 前额外运行 MarkTightlyCoupledBuffer，避免普通模式下产生无效 TCB clone 和 UB 压力

两条实现共享同一总体算法：构建 WorkItem、分析跨阶段输出、扩展存储、创建或标记新循环、迁移操作并安全回退。差异主要来自 RegBase 的向量函数、紧耦合 buffer、内存空间和后续 AVE lowering。阅读或修复时不能假设 A3 与 A5 源文件完全同步。

9. 生效条件与回退

CVPipelining 在以下条件下才可能产生实际改写：

  1. pipeline 在 MixedCV/自动 CV workspace 管理路径中加入该 pass；A5 还显式检查 enableMixedCV。
  2. CVPipelineMode 不是 Off。
  3. workspace multibuffer depth 大于 1。
  4. 函数中存在可划分为 Cube/Vector WorkItem 的 scf.for。
  5. 当前实现没有检测到被禁用的 AIC BatchMatmul loop。
  6. WorkItem、依赖、workspace、counter 和 yield 结构能够被安全迁移。

某个候选循环不满足条件时，pass 通常保留原循环并继续处理其他候选。内部在构造时保留 checkpoint；部分改写失败后会调用 revert，避免留下半完成 IR。调试“为什么没有排流水”时，不能只确认命令行开关，还要检查 WorklistBuilder 和依赖合法性是否让该循环回退。

10. 常见误解

“打开 CV Pipeline 就一定更快”

不一定。流水化增加 buffer、地址计算和同步，还可能提高 UB/L1/workspace 峰值。只有被隐藏的等待时间大于这些额外成本时，整体性能才会提高。

“CVPipelining 一个 pass 完成所有工作”

不对。它主要重构循环排布和跨阶段值；最终地址、同步和槽位轮转由其他 pass 完成。Skew 模式还必须结合 CreatePreload。

“多缓冲深度越大越好”

不对。更深的流水允许更多迭代在途，但会线性或近似线性增加某些 buffer 占用。深度应结合 Cube/Vector 时长、内存容量和同步成本选择。

“Dynamic 枚举代表动态流水已经完整实现”

不对。当前代码把 Dynamic 标记为 developing，核心分支只单独处理 Skew。另有基于 ssbuffer 的 DynamicCVPipeline 子系统，它不是这里的静态 CVPipelining 模式。

“没有看到 IR 变化就是 pass 没运行”

不一定。Pass 可能已经运行，但因为 depth、BatchMatmul、WorkItem 构建或依赖检查而跳过/回退。应查看 After_CVPipelining IR 和 debug 日志，而不是只看 pipeline 是否注册。

11. 调试观察点

建议沿以下阶段对比 IR：

  1. Before_CVPipelining：确认循环中 Cube/Vector 操作、核类型和 workspace 标记完整。
  2. After_CVPipelining：确认 WorkItem 对应的循环/scope、多缓冲维度和跨阶段 yield 是否形成。
  3. After_PlanMemory：确认扩展 buffer 地址不冲突、容量没有溢出。
  4. After_SplitMixKernel：确认 AIC/AIV 两侧的数据通道和同步锚点仍然对应。
  5. After_CreatePreload：Skew 模式检查 prime/steady/drain 的条件与 stage 次序。
  6. After_GraphSyncSolver：检查 set/wait 数量、方向和多缓冲 slot 是否匹配。
  7. After_EnableMultiBuffer：确认最终槽位轮转使用正确循环 IV 和深度。

遇到精度错误或 hang 时，优先检查三个问题：生产者和消费者是否使用同一逻辑 slot；PlanMemory 是否让仍在途的 buffer 错误复用同一地址；同步是否覆盖 prime、steady、drain 和最后一次槽位释放。CV Pipeline 的问题通常跨越多个 pass，仅检查 CVPipelining.cpp 往往不足以定位根因。

12. 最终总结

CV Pipeline 想实现的是 Cube 与 Vector 的跨迭代并行：把原本串行的 C(i) → V(i) 改造成稳定阶段中的 C(i) || V(i-1)。CVPipelining 通过 WorkItem 划分、依赖分析、循环重构和多缓冲通道建立这一基本结构。完整功能由 MarkMultiBuffer → CVPipelining → PlanMemory → GSS/同步 → CreatePreload（Skew）→ EnableMultiBuffer 共同完成。

从架构角度看，它是一个跨 pass 协议，而不是孤立的局部循环优化。它同时涉及调度、内存生命周期、跨核通信、同步和控制流，因此性能收益与正确性都依赖整条 pipeline。理解或调试 CV Pipeline 时，应始终沿“WorkItem 排布—buffer slot—地址规划—同步关系”四条主线一起观察。
