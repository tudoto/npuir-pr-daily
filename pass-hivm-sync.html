HIVM 同步机制与 GraphSyncSolver Pass

同步原理、求解流程与调试指南

1. 为什么需要同步

Ascend NPU 上的访存和计算指令会被分发到不同的硬件流水线（pipe）异步执行。MLIR 中相邻的两条指令，并不意味着它们在硬件上也按相同顺序完成。

例如：

GM --Load--> UB --Vector Compute--> UB --Store--> GM
       MTE2           V                  MTE3

如果没有同步，可能出现：

  • RAW（Read After Write）：Load 尚未写完 UB，Vector 已经开始读取；
  • WAR（Write After Read）：Vector 尚未读完旧数据，下一轮 Load 已覆盖同一块 UB；
  • WAW（Write After Write）：两个异步 pipe 同时写入重叠地址，完成顺序不确定。

纯读与纯读（RAR）通常不构成内存冲突。同步 pass 的目标，就是为真正存在冲突、且尚未被已有执行顺序约束的操作建立 happens-before 关系。

同步同时要满足两个目标：

  1. 正确性：任何可能发生的冲突都必须被覆盖，包括循环、分支和跨核路径；
  2. 性能：同步范围尽可能小，避免无谓阻塞并减少 event ID 占用。

2. 同步指令分类

2.1 pipe_barrier

hivm.pipe_barrier（底层常称 pipe_barrier 或 pipe_barrier(tpipe)）等待指定 pipe 在 barrier 之前已下发的任务完成。

它不需要 event ID，语义直接但同步范围较大。PIPE_ALL 会等待所有相关 pipe，通常是最保守、性能代价也最大的方案。

需要注意：pipe 是硬件指令分发/执行通道。一个过强的 barrier 不只是约束一对 producer/consumer，还会阻塞该 pipe 上其他本可并行的工作，进而影响整个流水。

2.2 set_flag / wait_flag

set_flag 和 wait_flag 用 event 建立两个 pipe 之间的精确依赖：

producer pipe:  producer -> set_flag(src_pipe, dst_pipe, event_id)
consumer pipe:  wait_flag(src_pipe, dst_pipe, event_id) -> consumer
  • set_flag：producer pipe 完成此前工作后发出事件；
  • wait_flag：consumer pipe 等待该事件后继续执行；
  • 匹配关系不仅包含 event ID，还包含源/目的 pipe；
  • intra-core GSS 的基础 event ID 数量为 8，通常是 0..7，但部分 pipe pair 会保留一个 ID，因此不能简单理解为所有场景都可自由使用 8 个 ID；
  • event ID 是有限硬件资源，需要分配、复用并检查生命周期是否重叠。

相比 barrier，set/wait 能只约束必要的 producer 和 consumer，通常更利于并行。

2.3 Unit flag

对于部分同 pipe 或硬件支持的固定同步关系，solver 可以使用 unit flag。它可以理解为无需普通 event ID 分配的专用同步通道。是否选用由目标架构、pipe pair 和 solver 配置决定，不宜把"同 pipe 冲突"一律等同于普通 set/wait。

2.4 跨核同步

MixedCV 场景中 AIC（Cube）和 AIV（Vector）属于不同核，使用：

  • sync_block_set
  • sync_block_wait

它们通过跨核计数/事件协调 Cube 与 Vector。跨核同步与 intra-core 的 set_flag / wait_flag 是两套机制，对应 CrossCoreGSS 或 DelayedCrossCoreGSS。

3. 哪些情况需要插入同步

3.1 正向同步：producer 到 consumer

同一次迭代内，先生产数据、后消费数据：

Load(MTE2) -> set(MTE2, V)
              wait(MTE2, V) -> Vector(V)

这是典型 RAW 依赖。通常让 set_flag 尽量靠近 producer，让 wait_flag 尽量靠近 consumer，以缩短被同步约束的区间。

"靠近"是性能原则，不是可以破坏控制流和硬件语义的绝对规则。

3.2 循环中的反向同步

循环复用同一块 buffer 时，当前迭代的 consumer 必须完成，下一次复用该槽位的 producer 才能覆盖它：

iteration i:      Vector 读取 slot[k] -> set(V, MTE2)
iteration i + N:  wait(V, MTE2) -> Load 覆盖 slot[k]

它在程序文本或循环展开后的 occurrence 顺序上表现为"反向"依赖，本质是 WAR：防止 buffer 被过早复用。

多缓冲时，每个 slot 的生命周期要彼此区分。GSS 通常会根据循环计数选择旋转 event ID，并形成：

  • prime（预置）：进入循环前，为可用 slot 建立初始 token；
  • steady state（稳态）：循环内 wait -> 使用/覆盖 -> set；
  • drain（排空）：退出循环后等待仍在途的事件，避免 token 泄漏或后续 kernel 误用。

这也是多缓冲同步最容易出现死锁或偶发精度问题的地方。

3.3 分支与 scope

"set 和 wait 必须在同 scope"更准确的表述是：

一对同步必须在控制流上可配对，并保证每条可能执行到 wait 的路径都有相应 set；不能让 set 和 wait 落入互斥分支或不平衡的循环次数中。

它们不一定必须具有字面上完全相同的 MLIR 父 region。solver 可以把同步移动到共同外层 scope，或者在边界生成同步。但必须保证：

  • set 和 wait 的动态执行次数匹配；
  • wait 不会等待一条未执行路径上的 set；
  • set 不会产生无人消费、并污染后续复用的事件；
  • 循环的首轮和末轮由 prime/drain 或条件 guard 正确处理。

3.4 跨核内存复用

在 MixedCV 中，AIC 与 AIV 可能通过 workspace 或 tightly-coupled buffer 交换数据。即使 SSA 上没有直接 use-def 链，只要物理地址区间重叠且两核访问顺序不确定，也需要跨核同步。

因此 GSS 分析的是"内存身份 + 访问效果 + pipe/core"，而不只是 SSA 依赖。

4. 同步插入的原则

4.1 正确覆盖内存冲突

需要覆盖 RAW、WAR 和 WAW，同时考虑：

  • 循环内与跨迭代冲突；
  • scf.for、scf.while 的 loop-carried value；
  • scf.if 等条件路径；
  • multi-buffer 的不同 slot；
  • AIC/AIV 跨核访问；
  • PlanMemory 后不同逻辑 buffer 对同一物理地址的复用。

4.2 缩短同步区间

理想放置为：

producer -> set ........ wait -> consumer

set 尽量晚、wait 尽量晚到仅在 consumer 前阻塞，通常能保留更多并行机会。但循环反向同步、分支合流和 scope 合法性可能要求将同步外提。

4.3 减少 event ID 压力

event ID 数量有限，solver 会：

  • 按 pipe pair 分配 ID（intra-core）；
  • 在生命周期不重叠时复用 ID；
  • 合并或移动反向同步；
  • 复用已存在的同步链；
  • 必要时降低 multi-event-ID 方案；
  • 最终无法满足时退化为 PIPE_ALL barrier。

因此 IR 中出现 PIPE_ALL 不一定是首选设计，也可能是 event ID 或同步放置求解失败后的保守 fallback。

4.4 覆盖所有动态执行路径

只看静态 MLIR 顺序不够。必须检查每个 operation 的动态 occurrence，尤其是循环首尾、条件分支和 unroll 后的重复实例。

5.1 Translate：MLIR 转内部 Sync IR

SyncSolverIRTranslator 将函数翻译为层次化结构：

Function
  Scope / Loop / Condition
    RWOperation
    SetFlagOp / WaitFlagOp / BarrierOp
    PlaceHolder / Anchor

可以把这一过程更细地理解为两步：

MLIR func.func
  -> FuncIR（保留 function/scope/condition/loop 层次）
  -> SyncIR（把层次结构展开为带 Occurrence 的线性分析序列）

这里的 "FuncIR" 是便于理解的叫法；在代码中对应以 Function、Scope、Loop、Condition、RWOperation 等 OperationBase 子类组成的内存对象树，并不存在一个独立的 MLIR FuncIR dialect。

翻译器收集：

  • function、scope、condition 和 loop；
  • 每条访存 op 的 read/write 集合；
  • op 所属 core 和读写 pipe；
  • loop-carried value 和分支 yield 的追溯关系；
  • 已有同步和可插入同步的位置。

随后把层次结构线性化为 occurrence 序列。每个 occurrence 具有 startIndex、endIndex 等位置字段。一个静态 op 在循环语义中可能对应不同动态 occurrence，因此 GSS 不能只按 Operation * 判断顺序。

5.1.1 syncIrIndex startIndex endIndex 三元组

GSS 的调试日志会按下面的形式打印 occurrence：

syncIrIndex startIndex endIndex Operation
0           0          61       Function(...)

因此笔记里的 0 0 61 一般表示：

  • 第一个 0：syncIrIndex，该 occurrence 在线性 syncIr vector 中的位置；
  • 第二个 0：startIndex，深度优先进入该节点时分配的全局序号；
  • 61：endIndex，遍历完所有子节点、退出该节点时分配的全局序号。

syncIrIndex 只对线性 occurrence 列表编号；startIndex/endIndex 则形成嵌套区间。若 A 是 B 的祖先，通常满足：

A.startIndex < B.startIndex <= B.endIndex < A.endIndex

这套区间同时用于表达 scope 包含关系和判断某条同步边在时间位置上是否可用。源码中的 globalIndex 在进入节点和退出节点时各递增一次，所以一个带很多子节点的 Function occurrence 很容易出现 (0, 61) 这样跨度较大的区间。

5.1.2 循环为何展开两份 occurrence

构建 SyncIR 时，syncIrBuilder 会把一个 loop body 展开两次，并用 loopSplitIndex 记录两份之间的分界：

Loop
  iteration 0 的 body occurrences
  -------- loopSplitIndex --------
  iteration 1 的 body occurrences

这不是把真实程序 unroll 两次，而是建立一个有限分析模型：两份相邻迭代已经足够表达大多数循环内和跨迭代冲突。

solver 随后分别生成：

  • 第一份迭代内部的 operation pair：分析同迭代正向依赖；
  • 第一份与第二份之间的 operation pair：分析跨迭代 buffer 复用；
  • 第二份内部的 pair 主要作为分析占位，通常标为 isUseless，避免重复生成等价同步。

因此"反向依赖拆成两条"更准确地说，是循环依赖被拆成两类约束：

同迭代：producer(i) -> consumer(i)       // 正向 RAW 等
跨迭代：consumer(i) -> producer(i + 1 或 i + N) // 反向 WAR/slot-release

对于 multi-buffer，下一次复用可能是 i + N 而非 i + 1，最终由 EventIdInfo、multi-buffer loop 和旋转 event ID 表达。这里的"两条"不是简单地无条件生成两对 set/wait；只有相应内存确实冲突、且图中没有已有同步路径时，才会形成 ConflictPair。

processingOrders 是待检查的有序 operation-occurrence 对。solver 会逐对判断它们是否：

  1. 存在读写内存冲突；
  2. 位于需要同步的不同 pipe/core；
  3. 尚未被已有同步路径覆盖。

5.1.3 processingOrders 到 ConflictPair

processingOrders 可以理解为候选键对列表，每一项至少关联：

(occ1, rwOp1) -> (occ2, rwOp2)

每个候选对依次经过：

  1. 过滤：排除顺序不可能成立、已经访问过、平行 loop 或 core 模式不匹配的 pair；
  2. 内存冲突判断：比较 rwOp1、rwOp2 的 read/write MemInfo；
  3. 确定同步端点：得到 source (core, pipe) 与 destination (core, pipe)；
  4. 选择放置点：计算 setOcc 与 waitOcc，处理分支、scope 和 loop 边界；
  5. 检查图覆盖：若已有 barrier 或同步链已经建立顺序，则跳过；
  6. 记录 ConflictPair：只有仍缺少顺序时，才记录同步区间、方向和 event 信息；
  7. 选择实现形式：根据 pipe/core、目标架构和 unit-flag 能力，最终物化为 pipe barrier、unit flag、普通 set/wait 或跨核 sync-block。

所以"相同 pipe 一定使用 barrier、不同 pipe 一定使用 set/wait"只能作为初步直觉，不能作为完整规则。相同 pipe 往往天然按队列顺序执行；只有存在特殊读写 pipe、unit-flag 能力或仍需强制完成语义时，才需要额外同步。最终选择还受目标架构和 fallback 策略影响。

5.2 MemInfo：判断是否访问同一内存

GSS 并非"相同参数就一律冲突"，实际按内存来源分类：

  • FuncArgInfo：同一函数中，只有同一个 block argument 才视为同一内存；Delayed CrossCoreGSS 在不同拆分函数间按相同参数序号对应；
  • PointerLikeInfo：对 hivm.pointer_cast、memref_ext.alloc_workspace 等，比较 address space、地址列表和分配大小，判断物理区间是否重叠；
  • AllocLikeInfo：判断是否来自同一个 alloc；
  • SubviewInfo：静态 subview 可进一步判断切片是否重叠，动态或无法证明不重叠时保守判冲突；
  • 其他情况：以底层 SSA value 相等作为 fallback。

函数参数之所以按同一 argument 判冲突，是因为它代表同一入口内存对象；拆分后的 AIC/AIV 函数虽然 argument SSA value 不同，但相同参数序号仍对应原 MIX 函数的同一对象。

对 pointer-like buffer，PlanMemory 产生的物理地址是关键依据。multi-buffer 时 addresses 可能包含多个 slot 地址，parentLoop 必须与 EnableMultiBuffer 选择地址 slot 的循环一致，否则可能出现"地址在按 A 循环旋转，event ID 却按 B 循环旋转"的错误。

5.3 ConflictPair：需要新增同步的基本单位

若两次访问冲突且没有已有顺序保证，solver 创建 ConflictPair。核心信息包括：

字段含义
op1 / op2发生冲突的两个 RWOperation
setOp / waitOpset/wait 的逻辑放置点
setOcc / waitOcc对应的动态 occurrence
setCorePipeInfo / waitCorePipeInfo源和目的 (core, pipe)
startIndex / endIndex同步边覆盖的 occurrence 区间
isInnerBackward是否为循环内部的反向/slot-release 同步
eventIdInfoID 数量、重复数、multi-buffer loop、preload offset 等
eventIdNode在 EventIdSolver 中参与生命周期与复用计算的节点
pinnedEventIdcustom macro 强制指定的 ID（如果存在）

前向同步的 set 通常位于 producer 后、wait 位于 consumer 前；反向同步则常表现为循环体开头 wait、循环体后部 set，并需要循环外 prime/drain。

5.4 GraphSolver：判断同步链能否传递

已有 ConflictPair 会被抽象为图上的边：

(source core, source pipe) --[startIndex, endIndex]-->
(destination core, destination pipe)

GraphSolver 使用 Dijkstra-like 搜索判断：从当前 producer pipe 出发，能否沿已有同步边到达 consumer pipe，并且每条边在 occurrence 时间区间上合法。

搜索中的关键条件是：

  • 下一条边的 startIndex 不能早于当前已经到达该 pipe 的位置；
  • 边的 endIndex 不能晚于目标 consumer 的截止位置；
  • 若能合法到达目标 pipe，说明已有同步链已经提供传递性 happens-before，无需新增同步。

以笔记中的例子为准：

1  Load GM                         [MTE2]
2  set MTE2 -> V
3  Load GM                         [MTE2]
4  wait MTE2 -> V
5  Vadd                            [V]
6  set V -> MTE3
7  Vector op                       [V]
8  wait V -> MTE3
9  Store GM                        [MTE3]

检查 1 与 9 是否还需要直接同步：

  1. 搜索从 (core, MTE2)、位置 1 开始；
  2. 通过同步边 [2, 4]，最早在位置 4 到达 V；
  3. [6, 8] 的起点 6 不早于 4，因此可继续沿该边，在位置 8 到达 MTE3；
  4. Store 位于位置 9，晚于到达位置 8；
  5. 已存在 MTE2 -> V -> MTE3 的传递同步链，所以不需要再插入直接的 MTE2 -> MTE3 同步。

5.4.1 反例：同步边存在，但时间上无法连接

考虑下面的顺序：

1  Load GM                         [MTE2]
2  set MTE2 -> V
3  set V -> MTE3
4  wait MTE2 -> V
5  Vadd                            [V]
6  Vector op                       [V]
7  Vector op                       [V]
8  wait V -> MTE3
9  Store GM                        [MTE3]

从静态 pipe 图上看，仍然存在：

MTE2 -> V -> MTE3

但两条同步边的有效区间是：

MTE2 -> V     [2, 4]
V    -> MTE3  [3, 8]

Dijkstra-like 搜索过程为：

  1. 从 MTE2 的位置 1 开始；
  2. 沿 [2, 4] 到达 V，此时 V 的最早可证明到达位置是 4；
  3. 尝试使用 [3, 8]，但该边的 startIndex = 3 < 4；
  4. 这意味着 V -> MTE3 的 set 在 MTE2 的完成事件到达 V 之前已经发生；
  5. 因此这个 set 可能只代表 V 更早的工作完成，不能证明位置 1 的 Load 已经完成；
  6. 搜索无法到达 MTE3，已有同步图不能覆盖 Load 与 Store 的冲突。

所以，即使 pipe 拓扑上存在 MTE2 -> V -> MTE3，时间区间不连续也不能形成 happens-before 链。solver 必须为位置 1 与位置 9 的冲突新增同步，或者把 V -> MTE3 的 set 移动到位置 4 之后，使两条边可以合法衔接。

可以把判断规则概括为：

下一条边.startIndex >= 当前 pipe 的最早到达位置
下一条边.endIndex   <= 目标 consumer 的截止位置

只满足 pipe 连通性、不满足 index 单调性，不能用于消除同步。

5.5 EventIdSolver：分配和复用 event ID

GraphSolver 确认需要新增同步后，EventIdSolver 为 ConflictPair 分配 ID。

intra-core 模式主要按 pipe pair 管理 event ID；cross-core 模式共享跨核分配器。分配时要考虑：

  • 两个同步区间的生命周期是否重叠；
  • multi-buffer 是否需要多个旋转 ID；
  • custom macro 是否通过 sync_event_slots 预留或 pin 了 ID；
  • 某些 pipe pair 的保留 ID；
  • preload/unroll 是否改变 set 与 wait 的迭代偏移。

只有不会造成事件串线、提前唤醒或死锁时，两个 ConflictPair 才能复用同一个 ID。

5.6 Emit：生成 HIVM 同步 op

求解完成后，solver 将 ConflictPair 物化到：

  • syncMapBefore：插入到某个 op 之前；
  • syncMapAfter：插入到某个 op 之后。

SyncSolverCodeGen 最终生成：

  • intra-core：hivm.set_flag、hivm.wait_flag、hivm.pipe_barrier；
  • cross-core：sync_block_set、sync_block_wait；
  • multi-buffer：按循环计数选择的动态/旋转 event ID；
  • 循环首尾：必要的 prime、drain 和条件 guard。

6. GraphSyncSolver 与 InjectSync 的区别

维度GraphSyncSolverInjectSync
分析方式内存冲突 + occurrence + 图可达性更保守的局部规则
同步粒度尽量精确往往插入更多 barrier
event ID完整分配、复用与 fallback逻辑相对简单
循环/multi-buffer支持反向边、旋转 ID、prime/drain优化能力较弱
优点性能更好、冗余同步更少简单、保守、适合对照排查
风险算法复杂，内存身份或 loop anchor 错误会导致隐蔽问题可能因同步过强损失性能

工程上可以用"关闭 GSS 后是否恢复正确"作为诊断信号，但这只说明问题可能位于 GSS、MemInfo 或 event ID 分配，并不能直接证明是哪一行逻辑出错。

7. 常见错误模式

7.1 缺少正向同步

现象：随机错、读到旧值；加 PIPE_ALL 后正确。

优先检查：

  • producer 的 write memory 和 consumer 的 read memory 是否被 MemInfo 判为冲突；
  • pipe/core 分类是否正确；
  • 是否错误地通过一条时间区间不合法的同步链判定为"已覆盖"。

7.2 循环首轮死锁

现象：第一次进入循环就卡住。

优先检查：反向同步每个旋转 event ID 是否都有循环前 prime set。

7.3 循环退出后死锁或污染后续执行

现象：循环末尾挂住，或当前 kernel 正确但后续 kernel 不稳定。

优先检查：循环后的 drain wait 是否齐全，event counter 是否有未消费 token。

7.4 multi-buffer 看似生效但结果错误

现象：IR 中有多地址和 arith.select，但只有某些迭代/slot 错误。

优先检查：

  • PointerLikeInfo.parentLoop；
  • event ID 旋转与地址 slot 旋转是否锚定同一循环；
  • eventIdNum 是否与 slot 数和 unroll 关系一致。

7.5 event ID 复用冲突

现象：偶发精度问题、wait 被错误 set 提前唤醒，或 custom macro 行为异常。

优先检查：

  • 相同 pipe pair 上两个 ConflictPair 的区间是否真正不重叠；
  • custom macro 的 pinned ID 是否与自动分配 ID 冲突；
  • unroll 后同一 event ID 是否承载了多组同时存活的 set/wait。

7.6 分支路径不平衡

现象：仅某个条件分支或边界 shape 挂死。

优先检查：是否存在执行到 wait、却跳过 set 的路径；以及同步是否应外提到共同 scope。

8. 阅读和调试同步 IR 的建议

建议按以下顺序检查：

  1. 找出首次发生冲突的两个操作；
  2. 确认它们的 read/write 内存、地址空间和物理区间；
  3. 确认源/目的 core 与 pipe；
  4. 确认是同迭代正向依赖，还是跨迭代反向依赖；
  5. 检查已有同步链是否在 occurrence 区间上真的可达；
  6. 检查 ConflictPair 的 set/wait 放置点；
  7. 检查 event ID 是否与其他存活区间冲突；
  8. 对 multi-buffer 检查 prime、稳态旋转和 drain；
  9. 对条件控制流检查所有动态路径是否平衡；
  10. 对 MixedCV 检查普通 CrossCoreGSS 与 PlanMemory 后 DelayedCrossCoreGSS 的结果。

9. 一句话总结

GraphSyncSolver 的核心不是"看到两个不同 pipe 就插同步"，而是：先用 MemInfo 判断两次动态内存访问是否真的冲突，再用 occurrence 和同步图证明是否已经存在合法的 happens-before 路径；只有证明失败时才创建 ConflictPair、分配 event ID，并在合法控制流位置生成最小同步。
